用开源 OpenModelica 加密 Modelica 模型库：SEMLA 规范、源码改造与全流程实操

这篇文章面向需要把一套 Modelica 库交付给客户、但不愿意暴露源码、也不想被 Dymola 锁死的工程师。文章不停留在”用 packagetool 打个包”的层面，而是把 SEMLA 协议、OpenModelica 源码里的 4 个改造点、桥接代码 5 个导出函数契约、完整的运行时调用链全部拆开，配上一个能跑通的 HelloEncrypted demo 与 16 个实测踩坑的回顾。读完之后，你应该能独立把 OMC 改造出一个带加密能力的 fork，把自家库打包成 .mol，并能在 OMC 和 Dymola 2025x 中跨工具加载。

文中的源码引用都基于 OpenModelica 1.27.0-dev 与 SEMLA master（2026-04 快照），所有命令在 Windows 11 x64 + UCRT64 上实测过。

一、问题：保护 Modelica 库源码的真实需求

商业级 Modelica 库典型有三类资产：

  1. 物理模型方程：往往是几年实验数据反推出来的经验关系式，是产品的核心壁垒。
  2. 架构封装方式：怎么把上千个组件拆成清晰的层级，本身就是知识。
  3. 参数与配方：写在模型默认值里的数字，可能就是工艺秘方。

把 .mo 直接发给客户等于把这三类资产一起发出去。Modelica 规范在 §18.9 给出了 Protection(access=Access.hide) 注解，但它只是”声明意图”——执行这套语义需要编译器在加载阶段做访问控制，并且源文件必须以加密形式存在，否则用户用 cat 就能看到方程。

Modelica 规范没有规定加密算法，每家工具历史上各做各的：

工具 加密格式 互操作性
Dymola 私有 .mol（早期） 只能 Dymola 加载
Dymola 2025x+ SEMLA .mol 可读 SEMLA 加密包
SimulationX 私有 + SEMLA（2025夏） 双轨
OpenModelica SEMLA .mol 需要打开 OM_ENABLE_ENCRYPTION

SEMLA 是 Modelon 主导开源的”工具厂商间互通的加密协议”，目前是 Modelica Association 标准化候选（PR #2931）。本质上它定义了两件事：

  • MLC 容器：.mol 文件长什么样、必填字段。
  • LVE 协议：工具进程和库厂商提供的守护进程之间怎么对话。

下面我们一层一层剥开它。

二、SEMLA 的两层结构：MLC + LVE

理解 SEMLA 的关键在于看清它是个”容器格式 + 通信协议”的复合体，而不是单纯的”对称加密文件”。

几点反直觉：

  • 解密不在工具里做，而是在 .library/ 目录里库厂商自己附带的 LVE 二进制里做。这意味着每个加密库都自带一份解密器，工具只是消费者。
  • 工具和 LVE 之间走 TLS 1.2 双向证书认证。tool 私钥嵌在 OMC 里，LVE 嵌着 tool 公钥白名单。陌生工具连过来直接拒绝。
  • 明文从不落盘：LVE 把解密后的 .mo 文本从 stdout 流出去，工具读完直接喂给 ANTLR3。

这套设计的安全假设是：你逆向出 OMC 也拿不到任何库的私钥（LVE 里的 AES 密钥才是核心），逆向 LVE 才有机会破开它对应的库——而每个厂商可以为每个客户/每个版本生成不同的 LVE。

manifest.xml 必填字段

必填项是 library.id、library.version.number、library.language.version。encryption/executable.platform 列出本 .mol 内置了哪些平台的 LVE——跨平台分发就要把所有平台的 LVE 都打进来。

package.order 为什么不加密

工具加载时需要先扫一遍包结构，决定加载顺序、解决类引用。如果 package.order 也加密，会陷入”要解密必须先启动 LVE，要启动 LVE 必须先读包结构”的鸡生蛋问题。所以 SEMLA 规定 package.order 与资源文件保持明文。这条规则意味着用户能看到包的目录树和类名，只是看不到方程——这正是规范允许的”接口可见，实现不可见”的边界。

五、密钥架构：3 组 4 类密钥

很多人第一次接触 SEMLA 会被密钥搞晕。其实就 4 类，分工很清晰：

名称 角色 嵌入位置 数量
Tool 私钥 工具向 LVE 证身份的 SSL 私钥 工具二进制（OMC / Dymola） 每个工具一对
Tool 公钥 LVE 端的工具白名单 每个 LVE 二进制 LVE 嵌入所有受信工具公钥
LVE 私钥 加/解密 .moc 内容的 RSA 私钥 packagetool + LVE 都嵌入同一份 每批 MLC 一对
Randomizer Key 把上述密钥在二进制里再混淆 packagetool / LVE / Tool 都用同一份 每批一份

关键不变式：同一批 .mol 用的 packagetool 与 LVE 必须用相同的 SSL 密钥 + 同一 Randomizer Key 编出来，否则跨设备运行时一定解密失败（这就是踩坑里的”P15 packagetool/LVE 来自不同 SEMLA build”）。

工程上的含义：

  • demo 阶段：3 个密钥目录扔仓库里没所谓。
  • 生产阶段：移到公司 Vault，CI 构建时短期 token 拉取。丢了 = 你已发出的所有 .mol 永久作废——这是事实上的”加密自杀”。

四个非平凡点必须记住：

  1. **不能直接 return parseEncryptedFile(...)**。它返回 char *（明文 buffer），不是 parse tree。必须先建 ANTLR 流，再 parseStream。
  2. ANTLR 函数名按版本宏切换。antlr3NewAsciiStringCopyStream 在 3.2 和 3.4 都不存在，链接时解析到错误地址，运行时 segfault。
  3. free(output_data) 必须在 parseStream 之后。ANTLR 文档说”copy stream”，实测是”持有引用直到 parseStream 完成”。提前 free 段错误。
  4. 大库 OOM 风险：上一代桥接代码忘 free 这个 buffer，加载 Modelica Standard Library（几百个 .moc）OOM。新写一定要 free。

七、桥接代码 parseEncryption.c：5 个导出函数契约

桥接代码本身是个 ~300 行的 C 文件。它的工作只有一个：把 OMC 的解析钩子翻译成 SEMLA 的 mlle_tool_* 调用。SEMLA 给的 tool 端 API 已经把协议状态机做好了，桥接代码不实现协议，只搬数据。

全局状态

整个 OMC 进程同时只能有一个 LVE 连接（SEMLA 的 mlle_* 用了文件级 static）。所以 OMC 的并行解析在看到 lveInstance != NULL 时强制单线程——这是上游 parallelParseFilesWork 的逻辑，不要去改。

十三、生产化路线：从 dummy 到真混淆

跑通 demo 绝不等于可以发给客户。SEMLA 默认带的 obfuscator 和 license_manager 都是 dummy，离生产差三个量级。

13.1 替换 dummy obfuscator

默认的 src/obfuscators/dummy/ 不混淆，AES 密钥几乎明放在 lve_win64.exe 里，反编译十分钟就能拿到。

策略上：每个 release 换 obfuscator 版本，使破解成本随版本上升而上升。

13.2 替换 dummy license_manager

默认的 src/license_managers/testingdummy/ 永远返回 YES。生产替换为：

  • 接 FlexNet / RLM / 自研 license server
  • 或最简版”机器码 + 到期日 + feature 列表”签名文件

License 检查逻辑在 LVE 端运行，所以可以做”启动时联网激活、本地缓存到期”的策略。

13.3 密钥进 Vault

3 个密钥目录从 git 移除，CI 构建时短期 token 拉取。同时建立”密钥换代记录”：哪一批 .mol 用哪一对密钥编出来的，新版本怎么和老版本平滑迁移。

13.4 flat code 防泄露

按 §10.3 跑 instantiateModel，grep 内部方程是否泄露。如果泄露：

  • 在源码端补 final / protected（最低成本）
  • patch OMC 的 instantiate 阶段（复杂，但根本）

十四、与 Dymola 私有加密的对比

什么时候选 SEMLA、什么时候选其他方案？

维度 Dymola 私有 .mol（旧） SEMLA .mol（开源） 不加密 .mo
工具锁定 只能 Dymola OMC + Dymola 2025x + Impact + SimulationX 2025 任意
加密算法 私有，黑盒 AES-256-CBC + RSA + TLS 1.2，可审计 无
Feature 级 license 支持 支持 不适用
跨平台 LVE 是 是（按平台打包多份） 不适用
自研加密强度 不可改 可改 obfuscator + license_manager 不适用
学习成本 低（GUI 点点） 高（需要编 OMC + SEMLA） 零
商业绑定 必须买 Dymola 授权 无（BSD-3-Clause） 无

选 SEMLA 的典型场景：

  • 想给客户多种工具选择（OMC 免费、Dymola 商用）
  • 想自己控制密钥和混淆算法
  • 想接自家 license server

选 Dymola 私有方案：

  • 公司全套都已经买了 Dymola，且不打算给非 Dymola 用户
  • 不想搞编译链路、想最快出包

十五、最佳实践清单

落地时直接照抄的硬规则：

加密前

  • 每个需要保护的 class 都加 Protection(access=Access.hide) 或 Access.documentation
  • package.order 完整列出所有子节点（packagetool 靠它确定文件列表）
  • 加密前先用普通 loadFile + simulate 跑通，确保源码端无 bug
  • manifest.xml 的 compatibility/tool/minversion 写明最低 OMC 版本

加密时

  • packagetool 和 LVE 必须来自同一次 SEMLA build，否则密钥不匹配
  • .library/ 下确保对应平台的 LVE 都打包了
  • 跨平台分发：Linux LVE 需要 chmod +x 标志位（packagetool 会做，但要 verify）
  • PEM 文件强制 LF 行尾（dos2unix）

加密后

  • list() 验证 hide class 返回空
  • simulate 验证仿真结果与原始 .mo 一致
  • instantiateModel flat code 不含秘密方程
  • Dymola 2025x 加载（如果跨工具）
  • Manifest 中标的 language version 与实际 .mo 兼容

密钥管理

  • 3 个密钥目录绝不进公开仓库
  • CI 构建时短期 token 拉取，不长期凭证
  • 每次密钥更新做一次”客户清单”——已发 .mol 必须重新打包并通知
  • 建立密钥换代记录（哪个版本用哪批密钥）

生产前 checklist

  • 替换 dummy obfuscator
  • 替换 dummy license_manager（接 FlexNet / RLM / 自研）
  • 移除 LVE 中的调试日志（fopen/fprintf 调试代码）
  • flat code 防泄露已 patch
  • 已在客户实际环境（不是开发机）走通整套流程

收尾

SEMLA + OpenModelica 这条路的核心价值是给 Modelica 库厂商一条不绑定 Dymola 的加密路径。代价是要自己维护一份 OMC fork、自己管密钥、自己替换 obfuscator——但换来的是工具链的自主权，以及”开源审计的安全保证”。

如果你的库会卖给客户、客户工具栈混合、且你想长期维持产品独立性，这条路值得走。如果你只是想内部团队用 Dymola，那直接 Dymola 私有格式更省事。

完整源码模板（含 parseEncryption.c 参考实现、.gitignore patch、CI 构建脚本）我在跟进的内部知识库里维护，后续会陆续把可以公开的部分整理到 GitHub。下一步打算写两篇姊妹文：一是「自研 obfuscator 怎么做到逆向成本平方级提升」，二是「LVE 接入 License Server 的工程实践」。
