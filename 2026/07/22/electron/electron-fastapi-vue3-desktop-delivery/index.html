Electron + Vue3 + Python FastAPI 桌面端交付全方案：动态端口、启动门与打包

一个工控上位机系统要交付给客户：算法在 Python（numpy/scipy/ctypes 调 C DLL），界面要 Vue3，最终得是一个双击就能跑的 Windows 安装包，客户内网、无外网、没有 Python 环境、可能连管理员权限都没有。

这类”前端 + 后端 + 桌面壳”三体结构的交付，真正难的从来不是写业务代码，而是这几件事：

  • 后端端口写死会撞车，客户机上 8765 可能被别的软件占着 —— 怎么拿到一个保证空闲的端口，并且让前端知道它是哪个？
  • Electron 窗口开出来的瞬间后端还没起来，用户点一下就是一片报错 —— 怎么做启动门？
  • 开发模式走 Vite proxy、生产模式走 file:// + 绝对地址，前端代码怎么只写一套？
  • Python 依赖怎么塞进安装包，PyInstaller 冻结后进程池为什么会疯狂自我复制？
  • 应用退出时 Python 子进程怎么保证不变成僵尸，下次启动怎么办？

本文以一个项目完整源码为样本，把这套交付方案从主进程启动时序讲到 NSIS 安装包，逐行分析关键实现，包含可直接复用的最小完整 Demo。

一、整体架构：三个进程，一条主线

先把进程关系摆清楚，后面所有设计都是从这张图推导出来的。

三条关键信息流：

流向 载体 内容
主进程 → Python spawn 命令行参数 + 环境变量 --host 127.0.0.1 --port <port>、PYTHONIOENCODING、DLL 模式
主进程 → 渲染进程 preload contextBridge + IPC 后端地址、启动进度、后端崩溃事件
渲染进程 → Python HTTP / WebSocket 业务请求，不经过主进程

注意最后一条：渲染进程直连 uvicorn，主进程不做请求代理。这是刻意的选择 —— 走 IPC 转发会让所有 HTTP 语义（流式、超时、WebSocket）都要重新实现一遍，收益为零。主进程只做三件事：分配端口、管生命周期、报启动状态。

二、动态端口：为什么不能写死，以及怎么拿

2.1 写死端口的三种死法

写死 8765 在开发机上没问题，交付到客户机上有三种典型翻车：

  1. 端口已被占用：某个本地软件、某个 Java 服务、某个上次没退干净的自己。uvicorn 启动即 OSError: [WinError 10048]，进程秒退，前端一片 ECONNREFUSED。
  2. 多开：用户装了两个版本，或者双击了两次图标。第二个实例抢不到端口。
  3. 最阴的一种：僵尸进程冒名应答。上次退出时 Python 没杀干净，还监听在 8765。新实例 spawn 失败，但健康检查 GET /health 却返回 200 —— 因为回答的是那个旧进程。界面正常进入，业务全是错的，用的还是上一次的数据库连接和板卡句柄。

第三种最值得警惕，它会把”启动失败”伪装成”启动成功”。后面 2.4 节专门处理它。

2.2 拿空闲端口的标准姿势：listen(0)

操作系统本身就提供了”给我一个空闲端口”的原语：绑定端口 0，内核从临时端口范围（Windows 默认 49152–65535）里挑一个当前未被占用的分配给你。

listen(0, '127.0.0.1') 而不是 listen(0)。 只绑回环地址。绑 0.0.0.0 会让 Windows 防火墙弹窗询问”是否允许此应用访问网络”，客户看到这个弹窗会打电话给你。上位机只服务本机，回环足够。

srv.unref()。 探测用的 server 不应该让 Node 事件循环因为它而保持存活。虽然马上就 close 了，但异常路径下 unref 能兜底。

srv.address() 的类型收窄。 Node 类型定义里 address() 返回 AddressInfo | string | null，字符串的情况是 Unix domain socket。TypeScript 下必须显式判断，不能直接 .port。

close 之后才 resolve。 如果在 close 的回调之前就把端口号交出去，调用方可能在 socket 真正释放前就让 Python 去绑，概率性地撞上 EADDRINUSE。

2.3 TOCTOU 窗口：这是可接受的

findFreePort 有一个理论缺陷：从我们 close 到 Python bind 之间存在一个时间窗口，另一个进程可能抢走这个端口。这是经典的 TOCTOU（Time-Of-Check-To-Time-Of-Use）竞态。

工程上有三种处理：

方案 做法 代价
忽略 直接 close 再交给子进程 窗口期约微秒级，本机单用户场景概率极低
传 socket 父进程持有 socket，通过 fd 继承传给子进程 Windows 上 Node → Python 的 fd 继承极其麻烦，uvicorn 需要 --fd 支持
子进程自选 Python 自己 listen(0) 后把端口打印到 stdout，父进程解析 彻底消除窗口，但父进程要解析 stdout、要处理”打印前就崩了”的情况

2.5 端口占用前置检测：用 listen 试探，不用 connect

网上大量教程用 net.connect(port) 探测端口占用：连上了说明被占，连不上说明空闲。这个逻辑在本场景下是错的，或者说答非所问。

我们要回答的问题不是”这个端口上有没有服务”，而是”我的子进程待会儿能不能 bind 成功”。这两者不等价：

  • 端口被绑在 0.0.0.0，你 connect 127.0.0.1 能连上，但你要绑 127.0.0.1 也确实会失败 —— 这种情况两种方法结论一致。
  • 端口处于 TIME_WAIT：connect 失败（没人在 accept），但不带 SO_REUSEADDR 的 bind 也会失败 —— 结论不一致，connect 法误判为空闲。
  • 端口被绑在另一个网卡地址上：connect 127.0.0.1 失败，bind 127.0.0.1 成功 —— 结论一致但推理过程是错的。

直接用你将来要用的方式去试探，这是最不容易出错的原则。

3.2 setProxy({ mode: ‘direct’ })

这行容易被忽略但在企业内网环境里是救命的。客户机器上常配了公司代理（PAC 脚本或系统代理），Chromium 默认会尊重系统代理设置。虽然大部分代理配置会对 127.0.0.1 走直连，但遇到配错的 PAC 脚本，你对本机后端的请求会被塞进代理，然后超时。

mode: 'direct' 一刀切禁用所有代理。本应用只和 localhost 通信，不需要任何代理。

3.3 preload：只暴露字符串和白名单方法

安全要点：

  • 绝不暴露 ipcRenderer 本体。exposeInMainWorld('ipc', ipcRenderer) 这种写法等于把整个主进程 IPC 面暴露给渲染进程，任意注入的脚本可以调用任意通道。
  • 通道名写死在 preload 文件里，不接受渲染进程传入的通道名。invoke: (channel, ...args) => ipcRenderer.invoke(channel, ...args) 是同样的问题，只是包了一层。
  • 文件扩展名是 .cts。项目 package.json 是 "type": "module"，但 Electron 的 preload 在 sandbox: false 下要求 CommonJS。.cts 让 tsc 编译出 .cjs，主进程里 preload: join(__dirname, 'preload.cjs')。

3.4 开发模式故意不注入地址

isDevMode 分支里 apiBase = ''，这不是偷懒。

开发模式下页面是从 http://localhost:5173 加载的，如果注入绝对地址 http://127.0.0.1:8765，浏览器会认为这是跨域请求（端口不同即跨域），需要后端配 CORS、需要处理 preflight。而走空串 + Vite proxy，请求是同源的 http://localhost:5173/api/xxx，由 Vite 转发到后端，零跨域问题，还顺便能在 Vite 的终端里看到请求日志。

前端侧的回退逻辑：

window.iControl?. 的可选链是为了支持 npm run dev:web —— 只跑 Vite、不起 Electron，纯浏览器调 UI。这时 window.iControl 是 undefined，全部走回退值，页面照样能用。

axios 那层：

于是形成一条约定：**所有业务 API 路径写相对路径，不带前导 /api**。

  • 开发：'projects' + baseURL '/api' → /api/projects → Vite rewrite → http://127.0.0.1:8765/projects
  • 生产：'projects' + baseURL 'http://127.0.0.1:54312' → http://127.0.0.1:54312/projects

四、启动门：窗口先出来，后端慢慢起

4.1 为什么必须有启动门

打包后的 Python 后端冷启动有多慢？实测：PyInstaller onedir 产物第一次启动要遍历 _internal/ 下上千个依赖文件、import numpy/scipy/pandas、初始化 SQLAlchemy 建表、加载 C DLL —— 在客户的机械硬盘 + 实时杀软扫描环境下，15 秒到 40 秒都见过。

没有启动门的话，这 40 秒里用户能干的事：点登录（报错）、点菜单（报错）、以为软件坏了并重启（雪上加霜，两个 Python 实例）。

启动门的设计目标：

  1. 窗口立刻出现，给用户明确的”在启动中”反馈
  2. 有进度条，让等待有预期
  3. 后端就绪前不允许进入任何业务页面
  4. 失败时给出可操作的错误信息 + 重试 + 日志
  5. 运行期后端崩了要能感知并恢复

五、Python 子进程管理

5.1 spawn：开发与生产两条路径

逐项说明：

ICONTROL_PYTHON： 开发模式下裸调 python 会走系统 PATH，可能不是项目的 conda 环境。scripts/dev.mjs 在启动 Electron 前主动探测：

注意不是用 conda run -n icontrol python -m server.main 直接跑后端。conda run 会多包一层进程，你 kill 掉 conda run 之后里面的 python 可能还活着 —— 又是一个僵尸进程来源。所以只用它问出解释器的绝对路径，然后直接 spawn 那个 exe。

PYTHONIOENCODING: 'utf-8'： Windows 控制台默认 GBK（cp936），Python 打印中文日志会 UnicodeEncodeError 直接崩掉进程。这个环境变量 + Python 侧的双保险：

windowsHide: true： 不加这个，Windows 上 spawn 一个 console 程序会弹出黑框。用户会去点那个黑框的关闭按钮，然后后端就没了。

stdio: ['ignore', 'pipe', 'pipe']： stdin 设 ignore 而非 inherit —— 后端不需要交互输入，继承 stdin 会让子进程在某些情况下阻塞等待。stdout/stderr 必须 pipe，用于日志收集。

?? 而非 || 的默认值： process.env.ICONTROL_DLL_CLIENT_KIND ?? (isDev ? 'mock' : 'real')。用 || 的话，显式设置的空串会被覆盖；用 ?? 只在 undefined/null 时兜底，尊重外部显式设置。

5.3 健康检查：进程退出即刻失败

关键点：

每轮循环先查 proc.exitCode。 这是”秒退”场景的救命逻辑：命令不存在、端口绑定失败、import 报错 —— Python 在 0.5 秒内就退出了，但如果只靠轮询超时，用户要盯着进度条爬 60 秒才看到错误。检查进程状态能把反馈时间从 60 秒压到 1 秒以内。

exitCode 和 signalCode 都要查：正常退出用前者，被信号杀死用后者，两者互斥（另一个为 null）。

res.resume()。 Node 的 http 响应流如果不消费，底层 socket 不会释放。轮询几十次之后会耗尽连接，健康检查开始莫名其妙地超时。这个坑很隐蔽，因为在快速成功的场景下（1-2 次轮询）根本不会暴露。

单次请求 timeout: 1000 + 轮询间隔 300ms。 单次超时防止某次请求 hang 住整个循环。300ms 是响应速度和 CPU 占用的折中 —— 更短没意义（后端不会在 100ms 内从”没起来”变成”起来了”），更长会让快速启动的场景白等。

主进程直连 uvicorn，不经 Vite proxy。 路径是 /health 不是 /api/health。主进程是 Node 环境，没有浏览器的同源限制，也不经过 Vite。这一点和渲染进程的路径规则不同，别搞混。

Windows 上的现实： proc.kill('SIGTERM') 在 Windows 上底层调的是 TerminateProcess，进程被直接干掉，Python 的 atexit / finally / FastAPI 的 lifespan shutdown 都不会执行。想要真正的优雅关闭，得走别的路：

方案 做法 适用性
直接 kill proc.kill() 最简单；后端没有必须清理的状态时够用
HTTP 关机端点 POST /shutdown 触发 server.should_exit = True 需要防护（只监听回环 + 校验来源）
stdin 信号 父进程写一行到子进程 stdin，Python 侧监听 要把 stdin 改成 pipe，Python 侧要起读线程
Job Object Windows 把子进程加入 Job，父进程死时自动清理 需要 native 模块，能解决”父进程被强杀”的孤儿问题

本项目走第一种。SQLite 是 WAL 模式，进程被强杀不会损坏数据库；录制中的 TDMS 文件最坏丢最后一个缓冲块，业务可接受。如果你的后端有必须 flush 的状态（比如写了一半的二进制文件），至少要上第二种。

父进程被强杀怎么办？ 用户在任务管理器里结束 Electron，before-quit 根本不会跑，Python 就成了孤儿，继续占着端口。生产模式下这不致命（下次启动会分配新端口），开发模式下就是 2.1 节的第三种死法。彻底解决要用 Windows Job Object（JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE），需要引入 native 模块，本项目权衡后没做，而是用前置端口检测 + 明确的错误提示来兜底。

5.6 重启后端：复用同一端口

重启必须复用同一端口。 window.iControl.apiBase 在页面加载时就固化了，重新分配端口的话前端还在往旧地址发请求。要换端口就得刷新页面（webContents.reload()），但那样会丢失用户的所有页面状态。

六、打包交付

6.1 构建流水线

四个产物的去向：

electron-builder.yml：

extraResources 而不是 files。 放进 files 的内容会被打进 app.asar（一个只读归档），Python 的 exe 在 asar 里无法执行 —— 它不是真实文件系统路径。extraResources 把目录原样复制到 resources/，主进程用 process.resourcesPath 定位。

perMachine: false。 装到 %LOCALAPPDATA%，不需要管理员权限。工控客户的机器经常是域账号无管理员权限，perMachine: true 会让安装直接失败。

base: './'（vite.config.ts）。 生产页面从 file:// 加载，绝对路径 /assets/index.js 会解析成 file:///assets/index.js（盘符根目录），全部 404。必须用相对路径。

6.2 PyInstaller：onedir 而非 onefile

onedir vs onefile：

onefile onedir
产物 单个 exe 目录（exe + _internal/）
启动 每次解压到 %TEMP%，慢且被杀软盯 直接跑
冷启动 数十秒（numpy/scipy 尤其慢） 秒级
反病毒 自解压行为高度可疑，误报率高 低
分发 反正都要塞进 NSIS 安装包 一样

对 Electron 场景，onefile 没有任何优势：产物最终都会被 electron-builder 打进安装包，用户看不到目录结构。而 onefile 的解压开销是每次启动都付的。

PYTHONNOUSERSITE: '1'。 这个坑很隐蔽：如果你不小心在 conda 环境外用 pip install --user 装过某个依赖，它会落在 %APPDATA%\Python\Python311\site-packages。PyInstaller 分析时能找到它（因为 sys.path 里有），打包成功；但打包环境和运行环境的 user site 不同，运行时可能缺东西。设了这个环境变量，PyInstaller 只从 conda 环境收集，装包时也要 pip install --no-user。

为什么用 .spec 文件而不是命令行参数。 一旦项目里出现 hiddenimports（动态 import 的模块 PyInstaller 静态分析不到）、collect_data_files（包内的非 .py 资源）、手动补 binaries（conda 的 libssl/libcrypto/libexpat 这类），命令行会长到无法维护，而且这些配置是踩坑踩出来的、需要版本控制的知识。固化到 main.spec 之后，build-python.mjs 只负责选对 Python 解释器和复制产物。

注意从 spec 构建时不能再传 --name / --collect-* 等生成期选项，PyInstaller 会直接报错拒绝。

6.3 冻结后的 multiprocessing 陷阱

这个坑值得单独一节。

原理：Windows 没有 fork，multiprocessing 的 spawn 方式是重新启动解释器并 import 主模块。正常 Python 环境下，子进程执行 python -c "from multiprocessing... " 加载你的模块；但 PyInstaller 冻结后，”解释器”就是 main.exe 本身 —— 子进程会重新执行整个 main.exe，也就是再起一个 FastAPI 服务。

症状极其诡异：调用某个用了进程池的接口 → 500 → 端口冲突日志 → 进程数暴涨。

freeze_support() 的作用是在冻结环境下检测”我是不是被 multiprocessing 拉起来的 worker”，如果是就走 worker 逻辑然后退出，不继续执行后面的代码。必须在任何模块级副作用之前调用 —— 放在 if __name__ == "__main__": 里是不够的，因为 app = create_app() 这种模块级语句会在它之前执行。

6.5 CORS

file:// 页面发起的请求，Origin 头是 null（或在某些 Chromium 版本下缺失）。allow_origins=["*"] 在这里是可接受的：服务只监听 127.0.0.1，外部机器根本连不上；且 allow_credentials 没开（开了的话 * 会失效，浏览器要求明确的 origin）。

如果你要更严格，可以 allow_origins=["null", "http://localhost:5173"]，但收益很小 —— 真正的边界是 --host 127.0.0.1。

十、最佳实践清单

端口

  1. 生产用 listen(0, '127.0.0.1') 让 OS 分配，开发固定端口以配合 Vite proxy 静态配置
  2. 绑定地址永远写 127.0.0.1，不写 0.0.0.0 —— 避免防火墙弹窗，也是最基本的安全边界
  3. 检测端口可用性用 listen 试探，不用 connect
  4. spawn 前必须做端口占用前置检测，错误信息里带上排查命令
  5. 重启后端复用同一端口，否则前端固化的 apiBase 会失效

启动时序

  1. 顺序不可变：resolvePort() → 写 process.env → createWindow() → 异步 launchBackend()
  2. 窗口立刻显示，后端在后台起，不要 await 后端就绪
  3. 启动页先订阅事件再拉当前态，两者都要有
  4. 进度条单调不减，健康检查阶段上限 95%，100% 只给 ready
  5. 路由层强制入口在启动页，改 hash 要在 createWebHashHistory() 之前

子进程

  1. stdio: ['ignore', 'pipe', 'pipe'] + windowsHide: true
  2. 三个日志源都要接：error 事件、stdout、stderr
  3. 健康检查每轮先查 proc.exitCode，秒退场景 1 秒内失败而不是等满超时
  4. res.resume() 消费响应体，防 socket 泄漏
  5. 用 stopping 标志区分主动停止与崩溃
  6. before-quit 里 preventDefault() + await stop + app.exit(0)
  7. 单实例锁放在文件最顶层
  8. 日志尾部缓冲 200 行放内存，通过 IPC 给启动页看

安全

  1. contextIsolation: true + nodeIntegration: false
  2. preload 只暴露字符串和写死通道名的白名单方法，绝不暴露 ipcRenderer 本体
  3. session.setProxy({ mode: 'direct' }) 避开企业代理
  4. 内网交付禁止任何 CDN / 外部 API 依赖

打包

  1. PyInstaller 用 onedir，不用 onefile
  2. 打包配置固化到版本化的 .spec 文件，构建脚本只管调用和复制
  3. PYTHONNOUSERSITE=1，装包用 pip install --no-user
  4. 模块顶部 multiprocessing.freeze_support()
  5. Python 产物走 extraResources，不进 asar
  6. vite base: './'，路由用 hash 模式
  7. nsis.perMachine: false
  8. 冻结环境下禁用 uvicorn --reload
