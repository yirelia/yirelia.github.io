微前端场景下的文件预览缓存设计：为什么我们抛弃了 TTL

一、从一个诡异的 Bug 说起

某天 QA 提了一个复现概率 < 10% 的 bug：

“切换工作空间后，点第一份 xlsx 预览，偶尔会弹出上一个空间的文件内容。”

三个问题一眼看出：

  1. key 只用 fileId——但不同工作空间下 fileId 可能相同（后端按 workspace 分库分表）
  2. 没有过期机制——签名 URL 早就在 5 分钟后失效，老旧 URL 被一直留着
  3. 没有失效订阅——切租户、切工作空间、登出都不清缓存

  • Scope（作用域）作为身份维度如何与缓存协同
  • AbortController 如何和缓存生命周期绑定，避免”缓存里有，但请求还在跑”的竞态

二、概念基础：TTL 缓存是怎么工作的

TTL 的含义是 Time To Live，给每条缓存项附带一个”存活时长”，过期自动作废。

2.1 典型 TTL 实现

三个假设隐含其中：

  • 假设 1：本地时钟 Date.now() 可信
  • 假设 2：写入时刻就是”有效起点”
  • 假设 3：TTL 是前端已知的量（由调用方传入）

这三条在传统 SPA 里大多成立，于是 TTL 成为最常见的缓存方案。

微前端架构下，至少五个新变量一起出现：

新变量：

  1. 多子应用共享一个预览组件，各自身份不同
  2. 签名 URL 由后端签发，过期时间由后端决定（前端并不知道签名策略）
  3. 用户随时可以切租户 / 切工作空间 / 登出
  4. 浏览器标签页可能被挂起数小时后再切回（本地时钟被系统休眠”拉长”）
  5. 用户可以手动改本地时钟

TTL 方案的三条假设全部塌陷。

三、TTL 在微前端下的四重失效

3.1 失效一：时钟漂移

现象：用户把系统时间调前 1 小时，或笔记本合盖休眠 3 小时再打开。

后果：

或者反过来：

根因：TTL 的”过期判定”锚定在前端本机时钟，前端时钟不可信。

3.2 失效二：前端不知道真实有效期

后端签发签名 URL 时，过期时间由后端策略决定（常见 5 min、15 min、1h、按文件类型分级）。前端强行写死 ttl: 5 * 60_000 只是对后端行为的猜测。

更严重的是，同一个系统里不同文件、不同操作签发的 URL 有效期可能不同。TTL 选不出一个通吃值。

3.3 失效三：身份维度未被编码

TTL 只表达”时间”一个维度。但缓存命中的正确性需要 ≥ 3 个维度：

  • 时间（是否过期）
  • 身份（当前 tenant / workspace / 用户是否和写入时一致）
  • 内容（资源本身有没有被后端更新）

TTL 方案里身份维度只能通过 key 拼接解决，而这恰恰是最容易被写错的地方——开头那个老 bug 就是 key 没拼 workspaceId。

3.4 失效四：失效广播缺失

TTL 是”懒失效”：只有在下次 get 时才会判定过期。但业务语义上，切租户应该立即把所有缓存清空——不能让 A 租户的 URL 有任何一点可能被 B 租户读到。

TTL 天然无法响应”切换工作空间”这类瞬时事件。

4.1 核心思路

项 TTL expiresAt
过期判定基准 Date.now() - createdAt > ttl expiresAt - Date.now() < skew
谁决定有效期 前端猜测 后端权威
多子应用一致性 各算各的 共享同一个 expiresAt
不同文件差异化 难 天然支持

4.2 时钟抖动边界（skewMs）

注意 skew 这个细节。严格比较 expiresAt < Date.now() 会导致一个临界问题：

网络 RTT + 后端时钟轻微不同步，就会在最后 1 秒产生 403。加一个 30 秒安全边界，让前端在离过期还剩 30s 时就主动认为”过期”，提前触发重新签发，避免临界态 403。

这个边界不消除时钟漂移，只是让前端倾向于偏保守，把可用窗口缩小 30s，用短暂的失效换更高的成功率。

4.3 expiresAt 仍然依赖 Date.now() 吗

是，但只在判定”还要不要使用”时使用，不作为过期基准。

  • TTL：Date.now() 用来算”已经过了多久”，一旦前端时钟跳 1h，TTL 就错 1h
  • expiresAt：Date.now() 用来回答”从现在出发，还有多少秒到 expiresAt”；即使前端时钟跳前，也只是提前认为过期并重新签发，最差结果是多一次网络请求，不会用到已失效 URL

后者把”时钟漂移”的代价从拿到错误的 URL降级为多发一次请求。

五、Scope：另一个维度的隔离

时间维度有了，身份维度怎么办？

5.1 PreviewScope 类型定义

两个方法各自对应一个职责：

  • getKey()：给缓存分租，不同 scope 不会互相命中
  • onInvalidate(cb)：身份变化时广播，让所有订阅者立即清空本地缓存

5.2 Shell 侧实现

三个失效源：

  1. tenantId 变化（切租户）
  2. workspace.containerId 变化（切工作空间）
  3. AUTH_EVENTS.LOGOUT 事件（登出）

只要任一触发，所有订阅者同步清空。

5.3 子应用侧实现（micro-app 场景）

为什么子应用的 onInvalidate 是 noop？

因为在 @micro-zoe/micro-app 架构下，切换工作空间会卸载整个子应用实例。子应用的缓存会随 Vue app 销毁一起 GC，不需要显式订阅。Shell 侧的 Host 才需要订阅（Shell 是常驻实例）。

5.4 为什么 Vue provide/inject 不能跨子应用

provide/inject 依赖 Vue 组件树。每个 micro-app 是一个独立的 Vue 实例，各自有自己的根组件、自己的 inject 上下文。Shell 的 provide 根本不会出现在子应用的 inject 查找链里。

结果是：每个子应用必须各自完整装配一遍 registry + scope + dataSource + Host。这是 micro-frontend 的沙箱代价。

六、源码剖析：Scope-aware LRU Cache

6.1 完整实现

6.2 逐行解读

第 23 行：const store = new Map<string, PreviewResource>();

用原生 Map。JS 的 Map 严格保留插入顺序，这正是 LRU 所需的”最新访问在尾部，最老在头部”语义。无需额外的双向链表。

第 26 行：buildKey(fileId) = ${scope.getKey()}:${fileId}

每次读写都现场求值 scope.getKey()。这意味着即使外部 scope 没来得及广播 invalidate，只要 scope 的 key 变了，旧缓存的 key 也不会被再次命中（新 key 拼出来不同）。这是一层被动防护。

第 28 行：scope.onInvalidate(() => store.clear())

订阅主动失效。切租户 / 切工作空间 / 登出时，Map 立刻清空。这是另一层防护。

被动 + 主动双保险：即使广播丢失，拼 key 也能拦住；即使 key 拼错，广播也能清干净。

第 31-34 行：touch(key, value) 先 delete 再 set

LRU 的核心技巧：想让某个 key “变新”，直接 delete + set，它就跳到 Map 的尾部。这是 Map 的 O(1) 操作（哈希表 + 链表）。

第 40 行：get 命中后也调用 touch

这是 LRU 和 FIFO 的分水岭。**访问也算一次”使用”**，否则退化成 FIFO。

第 48-52 行：while (store.size > limit) 淘汰

超限时从 store.keys().next()（即最老的）开始删，直到 size ≤ limit。用 while 而非 if 是为了应对极端情况下多于 1 条超限（虽然单次 set 通常只超 1 条）。

第 60 行：dispose() 取消订阅 + 清空

Host onBeforeUnmount 调用，防止内存泄漏（scope 还持有 listener 引用，Host 已经销毁）。

6.3 Controller 如何使用 Cache + Validator

四步：

  1. 读缓存
  2. 命中且未过期 → 直接返回
  3. 命中但过期 → 删除后重取
  4. 未命中 → 直接请求 + 存入

过期项主动删除而非”原地更新”，理由是避免”过期的 LRU 位”被新鲜项挤到后面去（LRU 的语义是”最近使用”，不是”最近写入”）。

七、AbortController 与缓存的协同

缓存层解决了”数据能否复用”，但还有一个容易被忽略的竞态：缓存里已经有，但请求仍在跑。

7.1 问题场景

可能出现：

  • 请求泄漏（用户已经关弹窗但请求还在占带宽）
  • 状态混乱（第二次 fetch 的 response 覆盖第一次的 cache）
  • 组件已卸载但回调仍在 setState → Vue 控制台红字

7.2 AbortGroup 独占语义

独占语义：同时最多有一个”活的” controller。spawn() 会先把上一个 abort 掉。

Controller 每次 open() 调用一次 spawn()：

“abort 时不设置 state“这条规则是关键：

  • 切换预览另一个文件 → 旧 controller abort → 旧分支 early return，不会污染新状态
  • 关闭弹窗 → abort → state 已经被 close() 置为 idle，不会被旧请求倒回 error
  • Host 卸载 → dispose() → abort → 幽灵请求被丢弃

7.3 Cache 与 Abort 的交互

有一个微妙的问题：abort 后要不要把 cache 里对应的 entry 也删掉？

答案：不要。

场景：

T=3 的 abort 不应该把 T=1 写入的 cache 清掉——那份数据是有效的。**abort 中止的是”尚未完成的 I/O”，不是”已经完成的结果”**。

9.4 expiresAt 字段后端没下发

症状：过期检测形同虚设。

原因：isExpired 在 expiresAt === undefined 时直接返回 false。

根治：

  • 后端推动补字段
  • 前端侧 fallback：对某些已知短寿命资源在 dataSource.resolve 内部手动打上 expiresAt = Date.now() + 5*60_000
  • 注意：这个 fallback 只是”再退一步”，仍然不如后端下发权威

9.5 生产环境偶现命中”跨租户”缓存

症状：概率极低但确实发生。

原因：scope.getKey() 在读写时求值，但 listener 里已经把 store 清空了。如果 getKey 所依赖的 store 变更和 invalidate 触发之间存在微观窗口（极少见），可能写入 A、读取 B。

修复：

  • 把 scope key 冻结到 entry 内：store.set(key, { resource, scopeKey: scope.getKey() })
  • 读取时再 check 一遍：if (entry.scopeKey !== scope.getKey()) return undefined

这是”三重保险”里的第三重。生产实践里前两重已足够，第三重为过度设计（除非真的观察到问题）。

十、TTL vs expiresAt：完整对照表

对比维度 TTL expiresAt
过期基准 前端本地时钟 Date.now() - createdAt 后端权威时间戳 expiresAt - Date.now()
写入方 前端猜一个值（如 5 分钟） 后端签发时写入
不同资源差异化 难（需区分 key 用不同 TTL） 天然支持（每个资源带自己的 expiresAt）
时钟漂移代价 拿到错误的 URL（严重） 多一次网络请求（可接受）
系统休眠 醒来立即全部”过期”，雪崩重取 仍按 expiresAt 判断，分批重取
多子应用一致性 各子应用自行 TTL，可能不一致 同一 expiresAt，所有消费者一致
抵御时钟攻击 用户改系统时间可让缓存永不过期 仍可被改，但 skew 边界保护了关键路径
与身份维度解耦 仅时间维度，身份靠 key 拼 同样靠 scope + key 拼，但配合 onInvalidate 能主动广播
实现复杂度 低 略高（多了 validator + skew）
后端负担 无 要求后端下发时间戳

结论：TTL 在 单 SPA + 无签名 URL + 不跨身份 的场景仍然合适。一旦引入微前端、多租户、签名 URL 任意一个，就应该切到 expiresAt + skew + onInvalidate 方案。

十一、最佳实践

11.1 缓存层设计 Checklist

  1. Key 必须包含身份维度：scope.key + resourceId，不要只用 resourceId
  2. 过期判定用后端时间戳：expiresAt 而非前端 ttl
  3. 加时钟抖动边界：skewMs ≥ 10s，保护临界态
  4. 主动失效广播：scope.onInvalidate + AUTH_EVENTS.LOGOUT
  5. 被动 key 防护：读写时现场求值 scope.getKey()，不 cache 住
  6. 过期项主动删除：不要等下次访问，见到过期就 delete
  7. 生命周期绑定 dispose：Host onBeforeUnmount 调用，取消订阅
  8. LRU 用原生 Map：O(1) 命中、touch、淘汰，无需双向链表
  9. AbortController 独占语义：每次 open 自动 abort 上一次
  10. abort 分支 early return：不写 state，不污染

11.2 代码结构建议

单一职责，每个文件 < 100 行。Controller 是唯一”知道所有基建”的地方，其他文件互相不依赖。

11.3 何时不要用这个方案

  • 完全离线的单 SPA：TTL 足矣
  • 资源本身永不变（如静态 CDN）：根本不需要过期判定，浏览器 HTTP 缓存就够
  • 小数据 + 强一致（如用户资料）：用 SWR / react-query 的 stale-while-revalidate 模式，每次都 revalidate
