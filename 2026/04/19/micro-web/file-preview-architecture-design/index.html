微前端文件预览组件的架构设计：从 9 宗设计债到可插拔预览平台

一、问题的起点

在一个多租户的微前端系统里，文件预览是一个看似简单但极易积累技术债的模块。它同时涉及：

  • 多种文件类型（CSV / TXT / 图片 / XML / Markdown / PDF / DOCX / XLSX…）
  • 多个子应用（数据管理 / 协同仿真 / 路由校验…）都要预览
  • 签名 URL 的时效性、租户隔离、工作空间隔离
  • 大文件的加载门禁与性能保护
  • 用户在任意时刻关闭 / 切换预览的中止语义

在很多团队里，这个模块从”写个弹窗”开始，慢慢演化成一堆分散在各子应用、各业务页面的重复代码。直到某一天 QA 提了一个跨租户串数据的 bug，大家才意识到要重新设计。

这篇文章完整记录了我们把一个有 9 处已知设计债的预览模块重构为可插拔、可扩展、跨子应用复用的预览平台的全部设计思路。涉及：

  • 现状痛点盘点（9 宗罪）
  • 分层架构设计（契约 → 基建 → 外壳 → 渲染器）
  • Registry 插件化的设计决策
  • Scope-aware 缓存 + AbortGroup 生命周期控制
  • Host 状态机 + Dialog 作用域插槽
  • 微前端场景下的集成模式（Shell vs 子应用）
  • 关键取舍与踩坑

读完你应当能在自己的项目里复制这套架构，或拿来评审现有预览实现的缺陷。

2.1 9 处具体设计债

# 问题 具体影响

2.2 根源分析

这 9 条表面上是不同问题，本质归为三类：

  1. 缺乏分层：业务、展示、数据获取、生命周期混在一起
  2. 缺乏契约：没有稳定的类型边界，加字段就是改天下
  3. 缺乏扩展点：新格式 = 改核心代码，而不是注册一个插件

所以重构不是”修 bug”，是重新设计边界。

三、设计目标

把 9 宗罪反推为 5 条设计原则：

  1. 单一职责：组件只做”拿到文件 → 拉取资源 → 渲染”，不涉及业务数据、权限、编辑
  2. 数据源可插拔：预览组件不直接调 API，调用方注入 DataSource
  3. 渲染器可扩展：新格式通过 Registry 注册，无需改核心代码
  4. 跨子应用复用：基建（Registry / Cache / Abort）在各子应用间保持一致语义
  5. 安全可控：Abort 贯穿全链路，Scope 隔离缓存，签名 URL 过期校验，文件大小门禁可配

几个明确的非目标（防止范围蔓延）：

  • 不做文件编辑
  • 不做文件上传
  • 不做权限判定（由调用方在数据源内完成）
  • 不做 SSR
  • 不做水印 / 禁复制等合规增强（只留 hook 位）

4.1 分层架构

五层职责清晰：

  • Contract：稳定的类型边界，所有层对它写入

五、核心契约设计

类型契约是这套架构最稳定的部分。所有字段 readonly，强制不可变。

5.1 五个设计要点

要点 1：禁止 blob 字段

如果允许 PreviewResource.blob: Blob，大文件会被整份加载进内存，GC 不回收。改成只走 URL，渲染器自己决定怎么 fetch（流式、range、虚拟滚动都在渲染器内部完成）。

要点 2：shouldPreview 返回 string 作为拒绝理由

比 boolean 多一种表达：”不是不支持，是有条件地拒绝”。例如 Office 渲染器返回 "文件过大（120MB），请下载后查看"，UI 直接把这串文案展示给用户，语义比”不支持该文件类型”准确。

要点 3：signal 必传到渲染器

渲染器内部 fetch / WebWorker / setTimeout 都要尊重这个 signal，这是全链路 abort 的前提。

要点 4：fileType 不绑扩展名

后端可能给 fileType: 'CSV'、也可能给 'text/csv'、甚至自定义编码。accepts 支持谓词（函数）可以任意匹配。

要点 5：PreviewState 是 discriminated union

TypeScript 会自动收窄字段可见性，UI 层无需手动判空。

六、Registry 插件机制

6.1 接口设计

三个方法覆盖所有场景：

  • register 返回反注册函数（自带清理），适合在 onMounted 注册 + onUnmounted 清理
  • resolve 返回 PreviewRenderer | null，匹配不到直接进入 unsupported 态
  • size 暴露只读计数，便于调试和单测断言

6.2 匹配策略

三个决策：

  1. 同名注册直接抛错：避免静默覆盖造成的”幽灵 bug”
  2. 优先级大者胜：业务方可以用更高 priority 覆盖内置渲染器
  3. accepts 支持 string[] 或谓词：string[] 足够简单场景，谓词覆盖复杂匹配（如 (file) => /\.(mo|modelica)$/i.test(file.name)）

七、Controller 状态机

状态机是这套架构的心脏——把四个基建编排成”一次预览”的完整流程。

7.1 接口

五个角色：

  • open / close：业务入口
  • markReady / markError：由 Host 代渲染器调（渲染器只 emit，Host 转调）
  • dispose：Host 卸载时调，清理所有副作用

7.2 open 的完整流程

六步都有明确职责，任何一步失败都有对应的状态终点。

7.3 两条”abort 分支 early return”规则

这行代码在 open 里出现两次：

  • 成功分支：如果等待 DataSource 期间被 abort，拿到的 resource 不要再 setState
  • 失败分支：如果抛的是 AbortError，不要设置 error 态

遵守这两条，整个状态机就不会被幽灵请求污染。违反任一条就会出现”关闭弹窗后 UI 闪过一个错误状态”。

7.4 fetchResource 的四步

这个函数把”读缓存 / 过期重取 / 写缓存”三个动作收敛在一起，open 只需要调用一次就能拿到新鲜资源。

八、基建层四件套

8.1 Registry（见第六章）

8.2 Scope-aware Cache

四个设计决策：

  1. 原生 Map 充当 LRU：Map 保留插入顺序 → 头部即”最老”，尾部即”最新”
  2. key 拼接 scope：身份维度内生到 key 里，scope 变了新 key 不会命中旧 entry（被动防护）
  3. onInvalidate 清空：scope 变化时主动清（主动防护）
  4. dispose 取消订阅：Host 卸载后避免 scope 持有野引用

被动 + 主动 + dispose 三重保险。

8.3 ResourceValidator

三条核心决策：

  1. **依赖后端下发的 expiresAt**：而非前端 TTL 猜测
  2. 提供 skewMs 抖动边界：默认 30s 提前判定，避免临界态 403
  3. expiresAt === undefined 视为永不过期：兼容后端没接过期字段的场景

8.4 AbortGroup

关键语义：独占。同时最多有一个”活的” controller。每次 spawn 自动 abort 上一个。

这一行代码直接解决了”用户快速切换文件”场景：前一次 fetch 还没回来，新一次 open 把它 abort 掉，结果不会污染 state。

九、Host + Dialog 外壳层

9.1 Host：状态机宿主

三个设计决策：

  1. 作用域插槽：把 { state, open, close } 暴露给父组件，方便自定义 UI（而不是只能用默认 Dialog）
  2. **默认 fallback 渲染 <FilePreviewDialog />**：不写 slot 时也能直接用
  3. **onBeforeUnmount 调 dispose**：组件级生命周期 = controller 生命周期

9.2 Dialog：默认 UI 壳

几个关键点：

  • 状态驱动 UI：没有 if (loading) ... else if (error) ... 散乱判断，只按 state.kind 分支
  • 渲染器 lazy load：defineAsyncComponent(renderer.loader)，不进主包
  • PreviewErrorBoundary 兜底：渲染器 throw 也不会白屏
  • **destroy-on-close**：关闭即销毁渲染器实例，释放内存

9.3 usePreview：业务入口

设计亮点：Host 缺失时返回 no-op + warnOnce。业务组件调 usePreview() 不会因为上层忘挂 Host 就崩溃，只是打一条 warn。

十一、关键设计决策与权衡

11.1 决策清单

# 决策 选择 备选 原因
D1 缓存过期策略 后端 expiresAt + skewMs 前端 TTL TTL 依赖本地时钟，时钟漂移后可能拿到无效 URL
D2 资源字段是否支持 blob 禁止 允许 opt-in 大文件驻留内存风险大于收益

D5 Scope 构造方 Shell / 子应用各自构造 预览包内置 Scope 依赖业务 store，预览包不该耦合
D6 provide/inject 还是全局单例 provide/inject 全局单例 微前端沙箱下单例泄漏更危险
D7 Dialog 是否内置 内置 + 可替换 只给 Host 80% 用户直接用默认，20% 用 slot 自定义
D8 渲染器加载方式 每个渲染器 defineAsyncComponent 主包内置 避免 Office 库让主包暴涨

11.2 为什么不用全局单例

最初考虑过”整个 window 一个预览实例”的方案，优点是子应用都不用装配。但有四个致命缺陷：

  1. 微前端沙箱：micro-app 卸载时可能不清理全局，下次启动带脏数据
  2. 多租户隔离：全局单例意味着所有租户共享一份 cache，scope 隔离失效
  3. HMR 友好性：热更新时全局单例不会重置，dev 体验差
  4. 单测困难：全局状态跨测试用例泄漏

provide/inject 跟 Vue 应用实例绑定，应用卸载就自动清理，是更”干净”的选择——代价是子应用必须各自装配一次。这个代价我们认为值得。

11.3 为什么 scope 要由外部构造

Scope 的 getKey 依赖业务 store（租户、工作空间）。如果预览包自己构造 scope，它就必须 import 业务 store → 包耦合爆炸。

反过来让外部构造：预览包只定义 PreviewScope 接口，Shell / 子应用各自实现。预览包零业务依赖。

12.1 Vite 库模式下动态 CSS 导入变空 shim

现象：Office 渲染器开发时可以跑，lib 构建后预览空白，Network 报 404 加载一个空 JS chunk。

Vite 的 lib 模式对动态 import('*.css') 的处理是：产出一个空的 shim JS chunk，然后把 CSS 内容丢到其他地方。这个 shim chunk 在 dev 里找不到真实文件会 404。

修复：改成静态 top-level 导入，让 Vite 正常把 CSS 合并进主 style.css：

代价：消费方必须显式 import '@your-org/file-preview/style.css'（因为现在 CSS 跟 JS 完全分离）。

12.2 Element Plus Dialog fullscreen + teleport + scoped 样式

现象：弹窗样式在 Component 内调整好了，一上线发现完全没生效。

原因：el-dialog 默认 append-to-body，Vue SFC scoped 样式基于 data-v-xxx 属性选择器，但 dialog 被 teleport 到 body 后，它的 DOM 里没有 data-v-xxx（或者祖先不在当前组件作用域）。

修复：样式分两段写

全局选择器管 “.my-preview-dialog 这个类名下的第三方结构”，scoped 管”自己 render 的节点”。

12.3 关闭弹窗后 “Cannot set reactive property on undefined”

现象：dev 控制台红字，用户关闭弹窗后后到的请求污染 state。

原因：fetch 返回后没检查 signal.aborted 就 setState。

修复：见第 7.3 节，两条 early return 规则。

12.4 签名 URL 临界态 403

现象：偶发 403，只在文件预览刚打开 1 秒内触发。

原因：URL 离过期只剩几秒，缓存命中时 isExpired 判为 false，但用户 fetch 时已经过期。

修复：ResourceValidator.skewMs = 30_000，提前 30 秒认定过期，触发重签。

12.5 场景：用户疯狂点列表切文件

现象：Network 面板一堆 pending 请求。

原因：没启用 AbortGroup 独占语义。

修复：每次 open 调用 abortGroup.spawn()，自动 abort 上一次的 controller。

十三、常见问题 FAQ

Q1：为什么每个子应用都要重复装配？不能共享一份？
A：Vue 的 provide / inject 是 Vue 应用实例作用域的，不跨 micro-app 边界。子应用是独立 Vue 实例，必须各自 provide。这是微前端沙箱的代价。

Q2：渲染器必须 emit ‘ready’ 吗？
A：是。Host 依靠 ‘ready’ 从 rendering 跃迁到 ready，隐藏加载态。漏 emit 会导致 loading 一直转。

Q3：为什么禁止 blob 字段？
A：大文件 blob 驻留内存且 GC 不回收。如果业务真的有本地 blob，让 DataSource 自己 URL.createObjectURL 转 URL 并在组件卸载时 revoke。

Q4：用户能感知缓存命中吗？
A：应当不能。Dialog destroy-on-close，缓存只是让 DataSource.resolve 省掉一次网络往返，UI 流程完全一样。

Q5：新增文件格式需要改核心代码吗？
A：不需要。registry.register({ name, accepts, loader }) 即可。业务代码里注册 + 在 onUnmounted 反注册。

Q6：能替换默认 Dialog 吗？
A：能。<FilePreviewHost v-slot="{ state, open, close }"> 拿到作用域插槽变量，自己渲染任意 UI。默认 Dialog 只是不写 slot 时的兜底。

Q7：SSR 能用吗？
A：v1 不支持。渲染器大量依赖 window / document / URL.createObjectURL。如果要做 SSR，需要给每个渲染器加 import.meta.env.SSR 分支。

十四、最佳实践 Checklist

14.1 设计期

  • 契约（types.ts）所有字段 readonly
  • 状态机用 discriminated union（kind 字段）
  • 渲染器的 accepts 同时支持 string[] 和谓词
  • 渲染器返回的组件通过 defineAsyncComponent 懒加载
  • DataSource 允许注入（便于单测 mock）

14.2 实现期

  • 缓存 key 编码 scope 身份
  • 缓存订阅 scope.onInvalidate
  • 验证器用 expiresAt + skewMs，不用 TTL
  • AbortGroup 独占语义（spawn 自动 abort 旧的）
  • 每个 await 后检查 signal.aborted → early return
  • Host onBeforeUnmount 调 dispose
  • 同名渲染器注册直接抛错
  • shouldPreview 返回 string 作为拒绝理由

14.3 集成期

  • Shell 和子应用各自装配（不共享）
  • Shell 的 Scope watch 租户 / 工作空间 / 登出
  • 子应用的 Scope 读 Shell 只读暴露的上下文
  • DataSource 尊重 signal，前后各检查一次
  • Host 放在 App.vue 顶层，一个子应用一个
  • 样式显式 import（如果采用静态 CSS 合并策略）

15.5 架构演进脉络

15.6 延伸阅读方向

  • 微前端沙箱与 Vue 应用实例隔离机制
  • Vue 3 defineAsyncComponent + Suspense 的加载态模型
  • AbortController 在浏览器 fetch / XHR / 自定义异步任务中的传递
  • 签名 URL 的过期语义（AWS S3 Presigned URL / OSS STS）
  • LRU 缓存的 Map 实现与 O(1) 复杂度证明

这套架构的精髓：把”一个预览弹窗”拆成五层，每层职责单一、契约稳定、可独立单测；跨子应用通过 provide/inject 而非全局单例解耦；缓存靠 scope + expiresAt 双维度隔离；生命周期靠 AbortGroup + dispose 兜底。九宗设计债一次性清零，后续扩展（新格式、新租户、新集成方）都只需要改插件，不改核心。
